1. Three worlds (and a fourth)

This node sits at the meeting point of three codebases. Keeping them straight is most of the battle, so they are colour-coded throughout this document.

  • Phlex is the data-flow framework. It loads plugins, builds a graph of nodes, and drives data through it. Crucially, Phlex has no explicit edges: it connects a producer to a consumer by matching product descriptors (see §6). It also has no config schema — it just hands each plugin a boost::json::object.
  • WCT (the Wire-Cell Toolkit) is the engine that does the physics. It has its own component system, its own graph (Pgrapher), and is configured by its own Jsonnet. Phlex knows nothing about it.
  • The integration is the code in this repo that makes a WCT graph look like a single Phlex node: wire-cell-phlex (the Executor classes + PHLEX modules), phlex-config (the generic node-config schema), and boost-config (turns a C++ struct into a documented, JSON-(de)serialisable, Jsonnet-emitting schema).
  • Configuration is the Jsonnet the user writes and the JSON it compiles to — the connective tissue between all three.
The one big idea. A user writes one Jsonnet object. Phlex reads part of it to build a graph; the integration reads part of it into a typed C++ struct; that struct configures a WCT graph. The same document is projected into three worlds. This walk-through follows that projection.

2. The example topology

The workflow is deliberately minimal: a synthetic source of DepoSets — the pure-Phlex generator wcph_deposet_gen, which hands out an empty in-memory SimpleDepoSet per event — feeds the deposet_filter transform, which runs each one through a trivial WCT graph (a passthrough) and emits it; an observer checks the result.

4. Workflow configuration config

Phlex consumes one top-level object with three keys: driver (emits the data-cell hierarchy), sources, and modules. We author it with the phlex.libsonnet DSL, which exists because Phlex forms edges from descriptors: the DSL lets a consumer reference a producer's output symbolically instead of copy-pasting creator/layer/suffix triples.

Two calls carry the wiring. src.output('deposet') returns a selector {creator:'input', layer:'event', suffix:'deposet'} — note the creator is input, not the source's label, because that is the convention Phlex providers use (see the source in §6). Passing it as the filter's inputs is the entire act of "connecting" the two.

The DSL is small and lives in the phlex-config package:

What Phlex actually receives

Compiling the Jsonnet yields the JSON below. Everything from here on is a reading of this object. Note the flat shape of a module entry: cpp (framework key — which lib<cpp>.so to load) sits beside inputs, outputs and the WCT keys wct_config/wct_plugins — all at top level, all opaque to Phlex and handed straight to our module.

Framework keys vs. opaque keys. Phlex itself only consumes cpp (the plugin library basename) and injects module_label = the map key ("deposet_filter"). Every other key in a module block — inputs, outputs, wct_config, wct_plugins, the legacy input_* — is passed verbatim to our module's registration function. That is the seam we build on.

5. JSON → typed config integration

Two different mechanisms read this module block. The WCT settings (wct_config, wct_plugins, …) are described by a plain C++ aggregate, ExecutorConfig, and parsed into it wholesale. The input/output wiring (inputs/outputs) is not parsed into a C++ struct — it is read directly, element by element, as an array of descriptor objects (see §6). boost-config's Documented<T> attaches a docstring to each aggregate field while staying transparent to use, and gives the struct boost::json (de)serialisation for free.

The wiring descriptor has a schema mirror in phlex-config — field-for-field the same shape the inputs/outputs objects carry, and field-for-field Phlex's own product_selector:

Why the field names matter. The C++ member names are the JSON keys (via boost::pfr reflection). ExecutorConfig::wct_config is the JSON path modules.deposet_filter.wct_config — top-level, no nesting. The module_label Phlex injects is folded in separately (see executor_config_from, §6), and the inputs/ outputs arrays are pulled out by hand rather than parsed into the struct.

6. Node registration phlex integration

A PHLEX plugin is a shared library that defines one entry point. The PHLEX_REGISTER_ALGORITHMS macro expands to that entry point and opens a function body receiving the graph handle m and the module's config. Here is the whole body for the filter:

register_function<In,Out> reads the two top-level arrays inputs and outputs, checks the port arity (one of each for a 1→1 transform), builds an ExecutorConfig (folding in module_label), and does the actual Phlex registration — m.transform(…).input_family(…).output_product_suffixes(…):

How edges actually form

The node has no wires. Instead:

  1. The filter's output product gets creator = {module_label, node-name} — here {deposet_filter, wcph_deposet_to_deposet} — and suffix deposet (from output_product_suffixes).
  2. The source explicitly stamps its product with creator "input":
  1. At graph finalisation, Phlex matches the filter's input_family selector {creator:'input', suffix:'deposet', layer:'event'} against the source's output {creator:'input', suffix:'deposet', layer:'event'} → edge formed. (Exactly one match is required; zero → tries providers/sources, else hard error; more than one → throws.)
  2. Likewise the observer's input_from:'deposet_filter' selector matches the filter's output creator on its module_label half.
Vocabulary trap. "creator" is a pair — {plugin=module_label, algorithm=node-name} — and matching succeeds on either half. That is why the node-name passed to m.transform is largely cosmetic (nobody selects by it here — the observer matches on the module_label half, deposet_filter) and why register_function can safely synthesise the node-name from the port types (wcph_deposet_to_deposet) rather than take it from config.

7. Executor & the WCT bridge integration wct

register_function constructed a FunctionExecutor<IDepoSet, IDepoSet>. That object is where the integration meets WCT. Its base, Executor, turns an ExecutorConfig into a configured (but not yet initialised) WireCell::Main:

FunctionExecutor<In,Out> is a thin wrapper over PortedExecutor<type_list<In>, type_list<Out>>, and it is that PortedExecutor base — not a bespoke subclass — that injects the boundary nodes. It no longer binds plain source_name/sink_name strings; it injects two code-valued (JSON) array TLAs, sources and sinks, via WireCell::Main::tla_code(...). Each is an array of WCT "inode" objects { type, name }, where type is the boundary class name from port_traits — so the config never hard-codes it:

The WCT side is a normal WCT Jsonnet — a function of the TLAs the Executor binds. Its signature is now the uniform (sources, sinks, app_name); the boundary components come straight out of the injected arrays, so no boundary class name is hard-coded here:

8. End-to-end trace

One DepoSet, all the way through:

#worldwhat happens
1phlexThe generate_layers driver emits an event data cell (3 of them, per total:3).
2phlexThe source (wcph_deposet_gen) provides a DepoSet product for that cell: creator input, suffix deposet, layer event.
3phlexPhlex's matcher (built once at finalisation) routes it to deposet_filter's input port — the edge inferred in §6.
4intgFunctionExecutor<IDepoSet,IDepoSet>::operator() runs (via the base run()): on the first call ensure_initialized() builds the WCT graph and finds the boundary ports; then it fills the boundary source with this event's deposet.
5wctrun_graph() drives the Pgrapher: DepoSetBoundarySource dequeues the deposet → (passthrough) → DepoSetBoundarySink enqueues the result.
6intgm_sink->drain() returns the result; operator() returns a DepoSet.
7phlexPhlex publishes it as a product with creator {deposet_filter, wcph_deposet_to_deposet}, suffix deposet.
8phlexThe observer's selector (input_from: deposet_filter) matches it; the observer runs its assertion.

9. Running it

Plain phlex -c resolves no Jsonnet import search path, so a DSL-authored workflow is run with phlexed (phlex + a subset of jsonnet's CLI flags). It is unofficial — used in demos and top-level tests, never baked into a package test.

Expected: Using configuration file: …deposet-filter.jsonnet then a clean exit — three events flow through with no assertion failures.

10. Discovery tooling integration

In principle a boost-config schema is self-describing: a plugin can export its config struct for a CLI to discover, and the schema can emit a documented Jsonnet factory — so schema and wire format are the same object. ExecutorConfig still carries the Documented<T> docstrings (§5) that would drive that.

The migrated shape modules, however, deliberately opt out. No shape module currently calls BOOST_CONFIG_EXPORT, and the earlier per-module <module>.libjsonnet generation was retired — there is no deposetfilterconfig.libjsonnet (nor any such file), and nothing is regenerated into share/jsonnet/wire_cell_phlex/. The reason: a single generic register_function<In,Out> now backs many node types, so a per-node config schema no longer maps cleanly onto one module. Config discovery is to be revisited in terms of node shapes later; it is future work, not part of the current build.

11. Glossary

Phlex

data cellA position in the data-layer hierarchy (a tree rooted at job; here job/event). The driver emits cells; products live in cells.
layerA named level of that tree (job, event, …). User-defined, not a fixed enum. Part of every product descriptor.
productA typed datum a node produces/consumes, identified by {creator, suffix, type} within a layer.
creatorWho produced a product: the pair {plugin = module_label, algorithm = node-name}. Matching hits on either half.
module_labelThe key of a module in the workflow's modules map. Phlex injects it into the config; it becomes the plugin half of the creator.
node-nameThe string passed to m.transform("…") etc.; the algorithm half of the creator.
product_selector{creator, layer, suffix, stage, type} — a consumer's query for an input. The connective currency of the graph.
familyThe set of products matching a selector across all cells of a layer — "creator/suffix ∈ layer". Hence input_family.
transform / observer / providerNode taxa: transform (≥1 in, ≥1 out), observer (in, returns void), provider/source (injects products, e.g. creator input).
driverEmits the data-cell hierarchy that drives the graph (here the stock generate_layers).
cppFramework key: the plugin shared-library basename → lib<cpp>.so, loaded from PHLEX_PLUGIN_PATH.
PHLEX_REGISTER_ALGORITHMSMacro defining a plugin's entry point; its body registers one or more nodes. Plural because one plugin may register several.

Wire-Cell Toolkit

WireCell::MainThe WCT job object: accumulates config/plugins/TLAs, then initialize()s and runs a graph. One per Executor instance.
component / NamedFactoryA WCT object identified by type:name in a global factory. The passthrough config creates three.
PgrapherA WCT IApplication that runs a graph of components given explicit edges. Our wct_app.
TLATop-Level Argument: a parameter of the WCT config function, bound by tla_var(k,v). How the Executor injects node names.
IDepoSetThe WCT interface for a set of energy depositions — the datum flowing through this example.
edgesWCT graphs do have explicit edges (in the Pgrapher config) — unlike Phlex. Do not conflate the two graphs.
